三、字号求解（可拖动）

网格 120 列 × 30 行 固定不变，容器尺寸可变。求一个字号 + 行高 + 字距， 让内容正好铺满可用区域。

字号— 行高倍数— 字距— 单格— 网格占用— 受限轴— 剩余—

竖直方向可以精确铺满：xterm 的 lineHeight 是倍数，直接解出 H / (rows × fs) 即可，但会钳在 [1.05, 1.60] —— 无限拉大行高只会让字距看起来断掉。 水平方向 letterSpacing 只吃整数像素，所以宽度会留下 <1 格像素的余量； 这点余量居中留白，不拉伸字形。字体只用系统栈（项目禁 CDN），所以 CJK 宽度的正确性取决于本机 装没装等宽 CJK 字体 —— 第一版会在启动时把实测到的单格宽高与理论值比对一次，不一致就提示。

把宽度拉大、高度压扁试试：因为网格被钉死在 120×30，短而宽的窗口会有大量横向 空间用不上（字号被高度卡住）。这不是算法缺陷，而是「尺寸由终端侧决定」的必然结果 —— 要改只能改服务端的 --cols/--rows，不能在浏览器里自适应。

四、四个分叉（已拍板）

  1. 布局：侧栏 + 顶栏状态条（本稿）
    备选：顶部标签页（更省空间，但每个会话的状态信息只能挤成一个点）； 侧栏 + 标签页都做（信息重复）。本稿选侧栏，因为会话名、cwd、退出码这些都有用。
  2. 字号求解：连续自适应（本稿默认）还是 0.5px 吸附？
    连续自适应能精确铺满，但改窗口大小时字号连续跳动； 吸附让字号稳定、字形更锐利，代价是边缘留几个像素。 上面第二个按钮就是吸附的实感，请拖一下再定。
  3. 一次只看一个会话（本稿），还是支持分屏同看多个？
    协议上一条 WebSocket = 一个客户端 = 最多订阅一个会话。分屏要同时开 N 条连接 （技术上没问题，后端已支持多客户端）。这会明显影响布局复杂度与资源占用，需要你定。
  4. 只管深色（本稿），还是深/浅可切？
    浅色不是「换个变量」那么简单：终端调色板、ANSI 16 色、光标、选区、滚动条、 xterm 的 minimumContrastRatio 都要各配一套并逐项验证对比度。
