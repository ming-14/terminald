# 架构

本文说明「为什么这样设计」。可执行的规则用测试强制（`tests/test_layering.py`），
不靠文档约束。

## 1. 形态

一个进程同时承担三种角色：

1. **终端守护**：持有会话、PTY、终端模型（`Hub` + `runtime`）
2. **实时通道**：`/ws` 广播字节流
3. **静态托管**：前端构建产物挂在 `/`

合在一起的理由是**会话坐标必须唯一**：offset、裁剪点、订阅表都活在进程内存里。

> **单进程是硬约束，不是默认值。** `uvicorn --workers N` 会让同一会话的两次 attach 落到
> 不同进程，各自持有互不相同的 offset——那是正确性问题，不是性能问题。要横向扩展必须先做
> 显式的会话分进程 + 网关路由，这一步没做之前不要改成多 worker。

前端由后端托管顺带消掉一整类问题：同源（不需要 CORS、不需要代理、不需要把端口编进构建产物）。

## 2. 分层

```
api ──→ service ──→ runtime ──→ core ──→ protocol
```

| 层 | 职责 | 硬约束（机器检查） |
|---|---|---|
| `protocol` | 帧格式、控制消息、转义序列边界扫描、共享向量 | 只依赖标准库 + pydantic |
| `core` | 日志、订阅对齐、出站队列、会话、注册表、端口 | 不 import `pywezterm` / `fastapi`；不依赖 `config` |
| `runtime` | 宿主适配、读/写线程、线程桥 | **唯一**可 import `pywezterm` 的层 |
| `service` | `Hub`：编排领域对象 + 线程 + 帧 | 不 import `fastapi`（传输无关） |
| `api` | ASGI 装配、REST、WS、来源校验 | **唯一**可 import `fastapi`/`starlette`/`uvicorn` 的层 |

分界的实际收益：offset、裁剪、重同步这些最容易写错的东西全在 `core`，可以脱离真实 PTY
与网络完整单测。`runtime` 与 `core` 之间只有 `ports.py` 里那几个 Protocol。

## 3. 内容真源：输出字节日志

**会话内容的真源是它产出的原始字节流，不是终端模型的渲染结果。**

- offset 从 0 开始、单调递增、永不回退；区间语义统一为半开 `[0, end)`
- 新客户端整段重放 `[0, end)` → 拿到的字节与「从头就在的客户端」**完全相同**
- 因为重放的是原始字节，冷状态（备用屏、字符集、tab stops、键盘栈、光标形状…）会随着
  这些字节**被重新执行**而一并还原，不需要逐个状态去保存和恢复
- 裁剪只发生在**转义序列边界**（`protocol/scan.py`）。从序列中间切断再重放会产生可见乱码，
  前置 RIS 也修不回来。多字节 UTF-8 字符同理（切断后重放会先打出几个替换字符）
- **客户端被要求从某个偏移开始解析时，那个偏移必须是解析状态干净的位置**：重建的对齐点
  （`Journal.replay_offset()`）与裁剪点（`safe_offset_at_or_after()`）都按这条选。
  重建时交付的是「快照 + 从对齐点起的字节」，对齐点若落在残缺序列里，客户端会把 `3m`
  这样的尾巴当普通文本画出来；回退到序列/字符起点则只是把这段字节重放一次，而残缺序列
  本来就没有效果，所以是补全而不是重复

这三点合起来给出一个可断言的结论：**多客户端「逐格一致」是构造出来的，不是对齐出来的**。
只要 cols/rows 一致、字节流一致、xterm.js 构建一致，两个客户端的 buffer 必然逐格相等。

### 3.1 两种状态的区分

| 状态 | 例子 | 重放原始字节能还原吗 |
|---|---|---|
| 由字节流决定的**热状态** | 屏幕内容、滚动位置、光标、SGR | 能 |
| 由字节流决定的**冷状态** | 备用屏、字符集（SI/SO）、tab stops、kitty 键盘栈、DECCKM/DECOM | 能（重放会重新执行这些序列） |
| **不**由字节流决定的状态 | 视图滚动偏移、选区 | 不需要还原（属于客户端本地视图） |

### 3.2 裁剪与唯一的有损路径

日志超预算时从头裁到「末尾 − 预算」，裁剪点对齐到转义序列边界。裁剪点之前的内容丢失，
这与原生终端 scrollback 写满后丢最早行是同一件事。

一旦客户端要的断点落在裁剪点之前，就只能用终端模型生成快照（RIS + 模式恢复 + scrollback
重放 + 可见区重绘）——**这是整套机制里唯一有保真损耗的路径**。它依赖两条不变量：

1. `fed_offset == journal.end_offset`（见 §9）。一旦被破坏，快照就会领先于对齐点，
   客户端会同时看到空洞与重复；
2. 对齐点是 `journal.replay_offset()`——**解析状态干净**的位置，不是日志末尾（§3 的最后一条）。
   末尾可能正卡在一个残缺序列里，直接对齐到那里会把参数字节当文本画出来。判断逻辑是纯函数 `core/sync.py:plan_attach`：

| 情形 | 决策 | 有损？ |
|---|---|---|
| 客户端断点在日志覆盖范围内 | `Resume(from, to)` 只补断档 | 否 |
| 全新客户端且 `start_offset == 0` | `Resume(0, end)` 整段重放 | 否 |
| 断点 < `start_offset` | `Rebuild(reason)` 走模型快照 | **是** |
| 断点 > `end_offset` | 抛 `OffsetAhead` | 报错，不静默重同步 |

最后一条是刻意的：客户端状态超前属于协议不一致，静默当作「全新客户端」会把真正的 bug 藏起来。

> `mode_restore_seq()` 的范围：**应用设过、且客户端能生效**的模式都恢复
> （1/6/7/12/25/45/66/1000–1003/1004/1006/1016/2004，以及 SM 4/20），并且只发**观察到过**的
> 那些——没设置过的不发，不用我们以为的默认值去覆盖客户端自己的配置。
>
> 仍有两个限制，都在 §12：被 ConPTY 吞掉的模式（鼠标、`?1h`、`?25l`、`?6h`、备用屏）拿不到，
> 以及 `?2026` 有意不恢复（打开它会让客户端一直缓冲渲染）。
> 前端 `debugState().modes` 是与之对照的**独立真相**（xterm.js 自己解析出来的那份）。

## 4. 尺寸模型

**`cols` / `rows` 是终端自身的属性，由终端侧决定；浏览器可视面积永不参与。**

- 配置里没有来自客户端的尺寸项；REST 的建会话请求也**不接受** `cols`/`rows`（额外字段直接 422）
- 三个终端侧属性 `cols` / `rows` / `scrollback` 由 `attached` 一次性交付给客户端；客户端只读
- 前端反过来做：已知 `cols`/`rows` 与容器可用像素，求一个让内容铺满的字号/行高/字距组合
  ——字号是因变量
- 因此协议里**两个方向都没有 resize 消息**：没有客户端改尺寸的路，也没有“终端侧改尺寸”
  的代码路径（所以没有 `sized` 这样的下行消息）；真要支持时再加，不留占位面
- 多客户端天然不会有尺寸分歧，这是「逐格一致」成立的前提之一

pywezterm 的 `Terminal` 构造时启用了锚顶 resize 语义（内容锚顶、光标绑定文本行），
所以万一将来需要 resize，行为也是确定的。

## 5. 输入路径

输入编码（DECCKM / kitty / CSI-u / SGR 鼠标 / bracketed paste）**由 xterm.js 依据应用下发的
模式完成**，服务端只做转发。

理由：同一套编码能力做两遍必然产生分歧。xterm.js 本来就要解析同一份字节流，它掌握的模式
信息与源模型同源，不需要再实现一份。

代价与配套手段：

- 走过「模型快照重建」的客户端，其模式可能缺失（见 3.2）。前端可以用 `term.modes` 读取
  自己真实生效的模式，与服务端下发的模式信息比对，把不一致暴露出来而不是静默错下去。
- xterm.js v6 **不支持 kitty 键盘协议**，而 pywezterm 的终端模型支持。应用查询时会被告知
  「支持 kitty」，但前端编不出 kitty 序列——这是当前的一处已知不一致。

### 5.1 输入方向的背压：让发送方停下来

输入方向的拥塞与输出方向相反：不是客户端跟不上，而是**客户端灌得比 PTY 写得快**
（往一个不读 stdin 的程序里粘贴一大段）。处理方式与输出方向同构：**显式状态 + 显式边界**，
而不是无限缓冲、也不是默默丢字节。

写队列按**字节**计量（`SessionRunner.submit_input`），带滞回的双水位：

| 事件 | 判定 | 动作 |
|---|---|---|
| 在途字节 `≥ input_high_bytes` | `HOLD` | 给该客户端下发 `input_hold{paused:true}`（只发一次） |
| 写线程把在途字节写回 `≤ input_low_bytes` | — | 经 `call_soon_threadsafe` 回事件循环，下发 `paused:false` |
| 在途字节 `≥ input_hard_bytes` | `OVERFLOW` | 该连接违约：`error{code:input_overflow}` + `1009` 断开 |

**为什么不是「停下来不再 receive()」**（那就等价于内核级背压、TCP 窗口关掉）：那不是留白，
它会把同一条连接上的**控制面一起堵住**——子进程不读 stdin 时暂停可能持续很久，而那正是
用户最需要「关掉这个卡住的会话」的时候；更糟的是对端在暂停期间断开，服务端会永远看不到
那条 disconnect（uvicorn 只是把它放进队列，不会取消 app 任务），于是任务、FD、订阅表里的
条目一起泄着，而它还参与焦点聚合与补流。让**发送方**停下来则两个问题都不存在。

滞回位（`_held`，只在**穿过**低水位的那一次回调）不是优化而是必需：没有它，每写出去一块
就会触发一次 `call_soon_threadsafe`，连续输出会把事件循环的回调队列刷爆。

### 5.2 补发必须分批：硬上限看的是**瞬时**队列深度

“放行”不等于“可以把整队一次倒出去”。硬上限衡量的是服务端写队列的瞬时深度，一次倒出多少
字节就是给它加多少字节，而**发放的时刻**两者不重合（放行只表示“队列已回落到低水位”）。
所以一个完全守规矩的客户端（暂缓就停、放行才发）如果一次倒出整队，会被当成违约而断开。

实测（`docs/audit.md` §2.3 场景 C：真服务 + 真 ConPTY，本端积压 4.75 MiB、硬上限 4 MiB；
该场景现由 `frontend/probe/input-hold.mjs` 与 `tests/test_input_backpressure.py` 守住）：

- 一次倒出 → `error{code:"input_overflow"}` + 关闭码 `1009`，**输入被截断**；
- 分批补发（每次 1 MiB）→ 暂缓/放行 6 个来回、零错误、子进程 sha256 与客户端构造的一致。

默认配置下同样可达：客户端的排队上限（16 MiB）恰好等于 `input_hard_bytes` 默认值。
所以这条约束是**协议的客户端义务**（见 `docs/protocol.md` §3）：

- 每次放行只送出 `heldFlushBytes`（前端默认 1 MiB，远小于任何合理的硬上限）；
- **过大的段要切开**——用户的粘贴在本端就是一大块字节，不切等于没限速；
- 剩下的部分靠一个进度定时器继续推（默认 50ms），这样服务端高水位比本端批量小时会重新
  下发暂缓（本端立即停手），比本端批量大时也不会把尾巴永远卡在本地；
- 只要积压非空，新输入就**一律入队**而不是直接发出（否则补发途中的按键会插到积压前面）。

不变量：

- **不丢字节**。判定只描述「发送方还能不能继续发」，字节一旦入队就一定会被写到 PTY。
- **水位的唯一依据是写队列**，与客户端数量无关：一个灌队列的客户端不会让另一个客户端被停发
  （每个会话的写队列是共享的，但 `input_held` 是每客户端状态，只发给真正灌满它的那个）。
- **宿主应答不参与水位**：DSR / 焦点应答是模型对流量的回复，必须无条件入队（否则模型永远收不到
  回复而卡死），它只计入在途字节的扣减，不会被拒绝。

对应测试：`tests/test_input_backpressure.py`（水位判定、滞回、每客户端状态、放行不丢字节）、
`tests/test_api.py::test_ignoring_input_hold_closes_the_connection_without_losing_bytes`。

## 6. 流控：按客户端游标补齐

每个客户端持有 `next_push_offset`——**它下一个需要收到的字节偏移**。有新输出时，服务端对每个
订阅者从该游标往日志末尾补齐（受发送队列水位限制），补到哪就把游标推进到哪。

由此得到一条决定性性质：**拥塞只会让推送暂停，绝不会丢字节**。没推的部分一直躺在日志里，
队列排空后从游标继续补。客户端之间不可能出现「有人悄悄少了一段」。

`Behind` 因此只在一个条件下发出：**客户端游标落后到日志已被裁掉的位置**。此时它必须发起
`Resync`，没有别的办法。

两种回程信号是分开的，且**各管一道闸**（这一点曾经是文档与代码不符的地方，见 `docs/audit.md` A4）：

| 信号 | 含义 | 效果 |
|---|---|---|
| 传输层排空 outbox → `on_drained` | 「socket 这一批写完了」 | 解除**发送队列水位**那一道限制，继续按游标补齐 |
| `Ack(offset)` | 「客户端已**渲染**到 offset」 | 更新 acked 基线，解除**解析窗口**那一道限制 |

### 6.1 解析窗口：`Ack` 到底在管什么

发送队列水位管的是「已交给 socket、还没写完」的字节，它**管不到客户端已经吃下的字节**：
只要客户端还接（内核 TCP 缓冲没满），服务端就能一直推。实测（见 `docs/audit.md` A4，
回归在 `backend/tests/test_push_window.py`）
一个「socket 很快、渲染很慢」的客户端可以让服务端把 **4 MiB 全推出去而 `acked` 停在 0**——
未解析积压跟着**输出总量**涨，与日志预算无关。

所以实时推送有一道自己的窗口：最多推到 `acked_offset + push_ahead_bytes`（默认 2 MiB），越过就停手，
等 `Ack` 把它往前推（`_on_ack` 的重试就是唯一的解锁信号）。加上窗口后同一构造的峰值：

| 构造（窗口 256 KiB、客户端每 1 MiB ack 一次） | 未确认积压峰值 |
|---|---|
| 无窗口（修复前） | 4064 KiB（≈ 输出总量） |
| 有窗口 | **256 KiB**（上界 = 窗口 + 一个分片） |

两条容易踩的边界：

- **窗口只对「证明过自己会 ack」的客户端生效**（`Client.ack_seen`：收到过至少一次真正推进的 `Ack`）。
  不会 ack 的实现（第三方客户端、或 ack 还没到）保持旧行为——一直推，而不是停在一个永远不会
  被解开的窗口上。代价是首包到首个 ack 之间的窗口管不着。
- **窗口 + 日志预算必须明显大于客户端的 ack 节奏**，否则被窗口卡住的客户端会被日志裁剪追上，
  于是走 `Behind` → 重建 → 再次被卡住的循环。那是**正确但昂贵**的收敛（内容不会错），
  不是丢字节；默认值（2 MiB 窗口 / 8 MiB 预算）对“每 256 KiB 或 300ms ack 一次”的前端很宽裕。

附加与重建的补齐**不受窗口限制**：那时 `acked_offset` 已被设成对齐点，`cursor - acked` 是负的，
所以“刷新后整段重放”“落后后快照重建”依旧一口气交付完。

### 与 tmux control mode 的关系

模型取自 tmux：每客户端一条队列 + 每 pane 一条队列、`client_offset{offset, queued}`
（「已写」与「已排」）、水位高低限、`%output` 块阻塞后续非 `%output` 块以保证顺序。

**但策略上故意不照搬两处**：

- tmux 客户端 → 服务端只有 `refresh-client -A '%N:pause|continue'`，**没有字节偏移**；而
  `continue` 会把 offset 直接跳到当前，也就是 pause 期间的数据被丢掉。我们改成客户端上报
  `resume` 偏移、服务端只补断档——精确续传代替「要么全丢、要么全发」。
- tmux 最后一道闸是缓冲超 64MB 就**杀掉客户端**。我们的对应物是日志裁剪 + 显式 `Behind`：
  客户端仍在，只是必须重同步。

## 7. 焦点聚合

多客户端的焦点必须在服务端**聚合成一个布尔量**再下发给应用（任一客户端聚焦即 `True`，
全部失焦才 `False`）。否则每个客户端各自上报 DECSET 1004，应用会收到互相矛盾的
FocusIn/FocusOut。客户端断开也会被聚合逻辑吸收，不会留下「永久聚焦」。

## 8. 会话生命周期

- 会话是服务端一等对象，生命周期与任何连接无关
- `attach` / `detach` 不影响会话；切换标签、刷新页面、关掉所有网页都不会中断会话里正在跑的程序
- 子进程退出**不销毁会话**：退出码上报，`journal` 与终端内容保留，仍可继续订阅
- 只有显式 `session.close`（或进程退出）才真正拆除

## 9. 线程模型

**所有会话状态（含终端模型）只在事件循环线程上改动。** 端口按线程归属切分
（`core/ports.py` 里的表）：读线程只做阻塞读，终端模型只由事件循环读写，PTY 只由写线程写。
因此 `core` 里不需要任何锁——并发正确性靠「单线程所有者 + 唯一写者」而不是加锁。

```
读线程 ──ThreadBridge(有界)──→ 事件循环 ──outbox──→ 发送循环 ──→ socket
   ↑                              ↑
 host.read()        host.ingest() + Hub 决策（无 await 临界区）
                                    ↓
                              写线程 ──→ PTY（客户端输入 + 宿主应答，唯一写者）
```

两条硬不变量（都有回归测试）：

- `host.ingest()` 与 `journal.append()` 在同一线程**相邻**执行 → `fed_offset` 恒等于
  `journal.end_offset`；于是 `snapshot()` 渲染期间不可能有任何 `feed` 插进来，快照恰是
  「重放 `[0, end)` 之后」的状态——重建路径的正确性就建在这一条上；
- 写 PTY 只有一个写者（写线程）：客户端输入与宿主应答共用一条 FIFO，字节序即入队序。

- 写 PTY 单独一个线程：写是阻塞操作，不能压在事件循环上
- `ThreadBridge` 有界：队列满时读线程等待，背压向 PTY 传导
- **`Pty` 自身的读缓冲也有上限**（绑定层已改）：高水位 1 MiB / 低水位 256 KiB，满了就
  停止从 PTY 读，让管道填满、子进程写阻塞——这才是背压真正落到 PTY 的那一步。可观测：
  `Pty.buffered_bytes()` 不会持续超过高水位（由契约测试钉住）。

> `Pty.write` 在**放掉 GIL** 之后才做阻塞写：`#[pymethods]` 默认全程持有 GIL，而 ConPTY 下
> 写入确实会阻塞（实测 4 MB ≈ 16–19 s）。已有的写线程正是为此存在：GIL 放掉之后，阻塞只
> 困住那一个线程，事件循环照常跑。
>
> **反过来说，写线程不是可选项。** 若在事件循环上调用 `Pty.write`，阻塞的就是循环自己：
> 所有会话、所有客户端、全部 HTTP 接口一起停摆（实测 15.7 s）。实测数据与回归测试见
> `docs/audit.md` A1。

## 10. 安全边界

当前版本**不做认证**。这不是「省事」，而是一个必须被围栏兜住的决定：这个进程在自己机器上开了
一个 shell，任何能连上该端口的人都能操作它。所以只有一件事——把暴露面钉死在回环地址上：

1. 服务器只 bind 回环（配置层保证，`--host` 给非回环地址直接拒绝启动）
2. WS 握手校验 `Host` / `Origin`：两者都必须是回环主机名

第 2 条不能省：浏览器**不会**对 WebSocket 施加 CORS 保护，而恶意网页可以对 `127.0.0.1:8765`
发起 WS 连接（DNS rebinding / 本地服务扫描）。校验 Origin 是这里唯一的防线。
将来加认证时，这两个检查仍要在认证之前执行。

前端侧遵循同样的口径：终端数据一律当不可信（禁 `innerHTML`）、禁 CDN、禁运行时下发 JS。

## 11. 前端与尺寸求解

前端的职责边界很窄：**它不做终端模拟，只做渲染与输入编码**。`cols`/`rows` 由 `attached`
消息给出，前端求一个放得进容器的字号——字号是因变量。

求解写在 `frontend/src/render/size.ts`，是纯函数，输入容器尺寸与**实测**的单格比例：

```
fsByWidth  = W / (cols × 单格宽/字号)
fsByHeight = H / (rows × 行高倍数)          ← 行高倍数是常量 1.3，不随容器变
fontSize   = min(fsByWidth, fsByHeight)，再向下吸附到 0.5px
格子宽 = fontSize × 单格宽/字号             ← 就是字符本身，不掺字距
格子高 = fontSize × 行高倍数
余量居中留白
```

**格子比例恒定，余量留白——不拿去撑间距。** 同一个 `cols × rows` 在任何窗口下都该长得
一模一样，所以一个字距都不加。反过来做（把余量分别塞进 `letterSpacing` 与 `lineHeight` 去
「铺满窗口」）会让字符间距随窗口漂：实测同一个 120×30，格子宽 ÷ 字号能在 0.62~0.90 之间
变，看起来像换了个字体。代价是容器宽高比与网格宽高比对不上时只能留白，这是刻意的取舍——
字形比例优先于铺满。

**字号没有下限，所以不存在「装不下」这种结果。** 容器再小也只是解出来的字号更小，网格始终
完整地铺在里面——宁可字小，也不截断网格、不缩放画布（那会让「逐格一致」这条前提失效），
也不改终端侧的 `cols`/`rows`（前端无权改）。`solveLayout` 因此从不返回空值：容器尺寸非正
属于调用方的编程错误（连画布都没有），直接抛错而不是返回一个假布局去骗渲染层。

唯一的边界来自渲染器本身：xterm 渲染字符的最小格子约为 **1px 宽 × 3px 高**（实测），
所以 120×30 的网格最小也要 120×90 像素。容器比这更小时字号会继续算小，但渲染结果不再
跟着变小，超出容器的部分被 `.term-host` 的 `overflow: hidden` 裁掉。这是渲染器的物理
下限，不是前端的判断——前端也不该拿它编一条「装不下」出来。

两个容易踩的点：

- **吸附只能向下**。向上取整会让 `cols × 单格宽 > W`，直接溢出容器。
- **单格比例必须实测**，不能用 0.6 之类的经验值——差一点在 120 列上就是可见的偏差。
  实测探针**不能用 `font` 简写属性**：它包含 `font-size`，会把 100px 覆盖掉，比例整体
  偏小若干倍（真踩过，比例量成 0.080，被合理性检查拦下）。

求解之后还有一环**实测校正**：xterm 的内部字符度量与我们量出来的可能差一点，所以应用后
量一次渲染结果，**按实测的溢出比例直接求出新字号**——网格尺寸与字号近似线性，所以
`新字号 = 旧字号 × min(容宽/网格宽, 容高/网格高)` 基本一轮就落到目标上，比一档一档地退
省得多。有界轮数只用来兜住取整留下的尾巴。校正发生时会把次数报出来——那说明模型与真实
度量不一致，值得知道而不是悄悄咽掉。

布局上有一处必须分开处理：`.xterm` 里同时装着网格和滚动条。**把整个 `.xterm` 居中会把
滚动条一起挪进去**（实测：网格 960 宽、容器 1052，滚动条悬在离右边缘 92px 处）。所以
`.xterm` 铺满容器（滚动条贴右边缘），只把 `.xterm-screen` 居中。

### 11.1 位置记忆：「刷新不丢」的第二层

内容不丢由 §3 的日志负责；**位置**（刚才在看哪个会话、视口停在哪一行）是客户端本地视图
状态（§3.1 表里那一行），服务端不知道也无需知道，所以它存在 `sessionStorage` 里
（`frontend/src/ui/remember.ts`）。

三条决定，每条都有具体理由：

| 决定 | 理由 |
|---|---|
| `sessionStorage` 而不是 `localStorage` | 它是 **Tab 级**的。多客户端是这个项目的核心场景，`localStorage` 会让一个标签页的切换改掉另一个标签页的记忆 |
| 只记会话 **id**，不记 offset | 刷新后的 xterm 是空的，按旧 offset 续传只会得到一屏空白（即 `attach.resume = null` 的含义）。模块干脆不提供记 offset 的入口，让错误写法没有落点 |
| 存不进/读不出来就当作「没有记忆」 | 隐私模式、沙箱 iframe、配额满都会抛。记忆是增强，缺了它终端必须照常工作；也不降级成内存实现——那会让它看起来在工作、刷新后却静默失效 |

**恢复时机是确定的**：`attached.offset` 是本次订阅的重放终点（服务端保证 `attached` 先于
字节），所以「已解析偏移 ≥ 它」就等于「重放字节全部进了 xterm」，此刻才滚动——比这更早
缓冲区还没那么长，比这更晚则要先回答「输出流什么时候停」（没有答案）。用户自己动手
（输入 / 滚轮 / 鼠标）就放弃恢复。

**两条不记的边界**：停在底部不记（跟随输出本来就是默认行为）；备用屏不记也不恢复
（没有 scrollback，行号一退出就整个失效）。后者在 Windows 10 上不可到达（见 §12）。

### 11.2 快捷键扩展：只接管「浏览器级」交互，一个字节都不上行

四个交互（F11 / Ctrl+C / Ctrl+V / 右键）不是应用逻辑，而是**浏览器与 xterm 默认行为之间的
冲突**（现状与实测见 `docs/audit.md` A12）。所以它落在 UI 层（`frontend/src/ui/shortcuts.ts`），
**不碰协议、不碰会话语义**：多客户端看到的字节流完全不受影响。

分层与其它前端模块一致：**纯决策 + 注入副作用的控制器**，零 DOM 依赖，能在 node 环境的
vitest 里直接驱动。

| 部分 | 职责 |
|---|---|
| `decideKeyAction(event, hasSelection)` | 纯函数：按键 → `fullscreen` / `copy` / `paste` / `pass`。一张表，没有副作用 |
| `Shortcuts` | 编排：拿 xterm 的返回值语义（`false` = 不要处理这个键）与浏览器的默认动作，把四条行为接上去 |
| `App` | 只负责接线：把真 xterm / `document` / `execCommand` / 失败提示注入进去 |

三条关键决定：

1. **`pass` 与 `paste` 的区别不是「管不管」，而是「要不要吞掉那个字节」。** 两者都**不**
   `preventDefault`：Ctrl+V 靠浏览器的原生粘贴命令 → xterm 自己的 `handlePasteEvent`（
   bracketed paste 等转换归它，我们不重新实现）。
2. **复制走浏览器自己的 `copy` 事件，不用 Clipboard API。** `navigator.clipboard.writeText`
   在没有授权时会被拒（无头与可视 Chromium 实测都是 `NotAllowedError`），而
   `clipboardData.setData` **没有权限模型**。所以 Ctrl+C 是「不 preventDefault，让浏览器自己复制」，
   右键是「`execCommand('copy')` 请求同一条命令」，两条路汇到同一个 `copy` 事件，
   而写入由 xterm 挂在 `.xterm` 上的监听器完成。
3. **「取消选区」只在一处发生**：挂在 `.term-host` 上的 `copy` 监听器（冒泡顺序保证它晚于
   xterm 的监听器，也就是「剪贴板已经写好」之后）。Ctrl+C / 右键 / 原生菜单的 Copy 共用这一个
   后置动作，而不是各写一遍。

**默认动作优先于自定义实现**是这一节的中心思想：这三条里有两件（粘贴、复制）本来就是浏览器
会做好的事，xterm 只是把它们的默认动作掐掉了。修法是「别掐」，而不是「自己重写一遍」。

诊断上多两个字段（`debugState().hasSelection` / `selectionLength`）：选区只有 canvas 渲染，
DOM 里没有任何痕迹，探针要断言「复制之后选区消失」就只能从这里读（与 `scrollback`、`modes`
同一个理由）。

**换 WebGL 渲染器之后，屏幕文本也归入这一类**（`debugState().screenLines`）：渲染器从 DOM
渲染器换成 WebGL 时，`RenderService` 会把 DomRenderer dispose 掉，而 `.xterm-rows` 正是它的
元素——换完之后 DOM 里**没有**任何屏幕文本，探针原先的取数口就不存在了。

边界必须说清：`screenLines` 读的是**模型里的文本**，它证明字节被解析进了缓冲区，**不证明**
那段文字被画到了像素上。像素那一层由探针自己读屏幕守（`frontend/probe/glyphs.mjs` 逐格数空洞，
`smoke.mjs` 数标记所在行的非底色像素）。渲染器换成本身带来的收益也只在像素层可见：方块与
盒线由终端自绘几何填满字符格，而格子高是字号的 1.3 倍，交给字体画必然留缝（实测同一图案：
自绘 0 空洞，字体字形 620 px 空洞）。

## 12. Windows / ConPTY 吞掉的模式（实测对照表）

Windows 上没有真 PTY，只有 ConPTY —— 它本身就是一层终端模拟器：**它会解析并吃掉一部分
模式设置序列，只吐出「渲染相关」的那部分**。后果是：那些模式应用设了，我们和客户端都无从
得知。这不是我们的 bug，但它决定了哪些功能在 Windows 上能work、哪些不能。

实测方式：让子进程写出序列，看它有没有出现在适配层 `host.read()` 拿到的原始字节里
（`MARKER` 文本作为「写入确实发生了」的对照）。

| 序列 | 是否到达 | 影响 |
|---|---|---|
| `?1004h` 焦点上报 | **是** | 可用（但见下条 §12.2） |
| `?2004h` bracketed paste | **是** | 可用 |
| `?7l` 自动换行关 / `?45h` 反向换行 / `4h` 插入 | **是** | 可恢复 |
| `?2026h` 同步输出 | **是** | 有意**不**恢复（逐帧瞬时模式，打开了会把画面冻住） |
| `?1000h`/`?1002h`/`?1006h`/`?1016h` 鼠标 | **否** | **鼠标上报在 Windows 上不可用**：客户端永远收不到鼠标模式，也就不会去捕获鼠标 |
| `?1h` DECCKM 应用光标键 | **否** | 应用想要 application 模式时，方向键行为会不对 |
| `?25l` 隐藏光标 / `?6h` origin | **否** | 重建时会丢 |
| `?1049h` 备用屏 | **否** | ConPTY 自己实现了备用屏（表现为清屏 + 空行），我们与客户端都看不见 |

Windows 11 有 `PSEUDOCONSOLE_PASSTHROUGH_MODE` 可以让 ConPTY 停止转译、原样透传 ——
**本机是 Windows 10（10.0.19045），没有这个模式**，所以上面这张表在可预见的范围内是固定的。

备用屏那一行有一个**对照组**可复现（`frontend/probe/conpty-alt-screen.mjs`）：同一个子进程
写 `\x1b[?1049h`，不经过 ConPTY（管道）时序列原样在（33 字节），经过 ConPTY 时不在，取
而代之是 ConPTY 自己的重绘（`\x1b[H` + 逐行 `\x1b[K`）。两个后果：客户端**不可能**在
这个平台上进入备用缓冲区（所以前端的备用屏保护在这里只能靠代码审查，端到端验不了）；
以及 TUI 程序的重绘全部发生在主缓冲区上，scrollback 语义与真终端不同。

### 12.1 输入方向的吞吐：ConPTY 本身就是瓶颈（实测 ~200 KiB/s）

那组数字来自一次隔离测量：把 Hub、journal、outbox、WebSocket 全部拿掉，直接构造
`PyweztermHost` 写入 8 MiB，分块大小取 64 KiB / 256 KiB / 1 MiB：

| 分块 | 写完耗时（全部阻塞在 PTY 写） | 子进程（全速读）收齐耗时 | 字节一致 |
|---|---|---|---|
| 64 KiB | 45.8 s | 38.7 s | 是 |
| 256 KiB | 44.0 s | 40.2 s | 是 |
| 1 MiB | 42.8 s | 40.2 s | 是 |

两个结论都很重要：

1. **分块大小不影响吞吐，也不丢字节** —— ConPTY 的输入侧本身就只有 ~190 KiB/s（约 4.6 s/MiB）。
   它同时解释了 A1 那组读数（4 MiB ≈ 16–19 s）的下半部分：那次阻塞不是“GIL 没放掉”，
   而是 ConPTY 真的就那么慢（放掉 GIL 只能保证“只堵住写线程自己”）。
2. 子进程读得再快也没用（全速读与每 64 KiB 睡 20ms 几乎一样），所以**输入回灌的节奏不是
   任何一端能选的**：往一个不（快）读 stdin 的程序里粘贴大段文本，就注定要经历这几十秒。
   正因如此，“暂缓 → 放行”必须是**显式状态**：用户得知道输入还在路上，而不是以为丢了。

写这个实验时又踩到一次自己制造的坑：第一版子进程用 `sys.stdin`（控制台当时是 cooked +
echo 模式），读到 **0 字节**——`^C`/`^D` 被控制台的行编辑器吃掉/当成 EOF。
测终端程序必须先把它切成原始 VT 输入（`ENABLE_VIRTUAL_TERMINAL_INPUT`）。

### 12.2 焦点：会不会上报两次？

服务端设计是「跨客户端聚合成一个布尔量再告诉应用」（`Hub._apply_focus` → `host.set_focus`
→ 终端模型写 `\x1b[I`/`\x1b[O` 到 PTY）。但 `?1004h` **能**到达客户端，于是 xterm.js 也会
按该模式自己在聚焦/失焦时经 `onData` 吐出同样的序列，被当作 INPUT 转发进同一个 PTY ——
应用就会收到两份互相矛盾的焦点事件，正好是服务端聚合要避免的事。

**结论：会。** 实测（真实浏览器探针，钩住 `WebSocket.send`）：客户端 `sendFocusMode` 为 true
时，聚焦会发出二进制 `INPUT` 帧 `1b5b49`（`ESC [ I`），失焦发 `1b5b4f`（`ESC [ O`）——
而服务端也会写一份，应用收到两份。

**已修，取「服务端独占」**：前端在 `onData` 输入路径上滤掉这两个序列。为什么不反过来
（让 xterm.js 独占）：那样每个客户端会各自上报，`N` 个客户端就会给出 `N` 份互相矛盾的
焦点事件，正是服务端聚合要解决的那个问题。代价是「粘贴恰好是这两个字节序列的文本」会被丢掉
——刻意接受：焦点状态正确远比那种粘贴重要。

该行为已在主探针里钉住（`npm run probe`：断言客户端进入 1004 模式、但聚焦/失焦都不再发出
焦点序列）。前端 `debugState().modes` 是与服务端状态对照的**独立真相**（xterm.js 自己解析
出来的那一份）。

## 13. 已知缺口

按「会不会影响正确性」排序：

1. **快照重建的模式覆盖受 ConPTY 限制**：绑定层的模式扫描器已扩到「应用设过、且客户端能
   生效」的全部模式（1/6/7/12/25/45/66/1000-1003/1004/1006/1016/2004 与 SM 4/20），
   但 §12 里被 ConPTY 吞掉的那几项**无从恢复**——不是没写，是拿不到。
2. **ConPTY 下应用设的第一次标题会丢**（已知行为，已被契约测试钉住）：ConPTY 把标题序列
   规范化成 `OSC 0`，而 `enable_conpty_quirks()` 会抑制**第一个** OSC 0（本意是吞掉 ConPTY
   自动发出的 shell 路径）。见 `test_contract_pywezterm.py`。
3. **xterm.js v6 不支持 kitty 键盘协议**（见 §5），而后端模型支持——应用会被应答「支持」
   但前端编不出该序列。
4. **鼠标上报在 Windows 上不可用**：见 §12——Windows 10 没有 ConPTY 的 passthrough 模式。

| `protocol/vectors/shapes.json` | **每条**下行消息的字段与类型（由模型生成） | 后端断言「重新生成 == 文件」；前端断言「自己的校验表 == 文件」 |

## 15. 验证分层（改完之后怎么看它真的对）

| 层 | 位置 | 回答什么问题 |
|---|---|---|
| 单测 | `backend/tests/`（默认套件） | 逻辑与状态机（fake 宿主，确定性、快） |
| 契约测试 | `backend/tests/ -m contract` | 接上真实 pywezterm + ConPTY 后还成不成立 |
| 浏览器探针 | `frontend/probe/`（八个，自带服务器） | 真 Chromium 里的渲染与**像素**（方块/盒线连没连、中文双宽）、键盘/鼠标/剪贴板、刷新与多客户端同步 |

三层各自能红才算守得住：探针的失败必须是非零退出码，断言不能是恒真的（第二轮的 V1–V6
就是两个探针里的恒真断言、两个写死的本机路径与一份只覆盖 6/18 消息的契约，见 `docs/audit.md` §2.7）。
